# V11.4.3 Security and State Integrity

This change hardens existing contracts without changing historical transactions,
deploying, running migrations, or introducing a user identity model. All database
regressions use isolated PGlite instances. Provider operations in tests are mocked.

## Verified root causes and fixes

| Defect | Root cause | Contained correction |
| --- | --- | --- |
| Malformed financial input returned ALLOW | Numeric coercion and comparison-only policy checks | Strict numeric/currency/quantity schemas, currency precision checks and fail-closed policy checks; legacy purchase and refund boundaries hardened too |
| Discovery could overwrite paid sessions | Unconditional SEARCHING update | Atomic CREATED-only claim requiring no selected product or payment evidence; all other states rejected |
| Competing STEP-UP actions left inconsistent effects | Limit/token writes happened before conditional request resolution, whose result was ignored | Single SQL statement claims request under wallet lock and atomically writes the winning limit/token and linked session transition; losing or expired resolutions have no effects |
| Orphan one-time grants could be consumed | Consumption did not check the parent request outcome | Consume only an APPROVED_ONCE, unexpired parent request; existing same-session recovery remains idempotent |
| Receipt verification checked signature presence | Read path did not recompute payload hash or HMAC | Independent canonical hash and Web Crypto HMAC verification, full audit validation, evidence-head membership and receipt/session/wallet identity checks |
| /v1 browser authentication failed preflight | Global OPTIONS handling shadowed route-specific headers | Global authorization/x-intentlock-key header support, requested method/header validation and optional exact origin allowlist applied to actual responses too |
| Web and external authorization skipped queue risk logic | Risk tightening existed only in the queue | Shared assessAndTighten decision used by session orchestration and external authorization; queue delegates to session runner; capture preserves risk-only consent requirements |
| Queue execution lost configuration | Helpers rebuilt partial environment objects | Complete environment copies preserve payment, commerce, FX, PayeeLock and future configuration |
| Bose/Boat demo selected Sony | Demo connector matched generic shared words across brands | Demo discovery respects explicitly requested fixture brands/model; UI displays actual backend decision/selected product, not promised scenario decisions |
| UI overstated verified execution | Hardcoded global success claims and status-derived milestones | Remove global capture-verification claim; complete receipt badge requires all verification gates; runner milestones require events and never infer proof from session status |
| Refresh rejection / production localhost | Uncaught polling promise and silent API fallback | Refresh catches and reports errors; centralized runtime API URL validation fails explicitly in production |

No new SQL function or production migration is required: atomic statements use the
existing V10.2/V10.4/V10.6/V11 schema. Installed schema versions remain an operator
precondition; this work did not connect to or alter production databases.

Historical receipts remain readable. Missing keys, old/incomplete evidence, or
invalid signatures now produce an unverified result rather than a false VERIFIED
badge. Existing LIMIT_RAISED sessions remain recognized during payment revalidation.
Historical orphan grants on rejected requests are intentionally rejected.

CORS_ALLOWED_ORIGINS is an optional comma-separated list of exact origins.
Without it, existing wildcard-origin compatibility remains. With it, unlisted
browser origins are rejected on preflight and actual requests. No credentials
mode or cookie authentication is introduced. CORS is not authentication.

The WhatsApp component already disabled expired/unconfigured QR/link entry; this
behavior is retained. Runtime sandbox availability now additionally requires
configured PayPal credentials/webhook metadata. This is a configuration check,
not proof of provider connectivity, registered webhook correctness or capture.

## Unresolved architectural release blockers

### P0: public financial control and resource ownership

`src/wallets/routes.ts`, `src/sessions/routes.ts`,
`src/session-payments/routes.ts`, and read operations in
`src/trust-center/routes.ts`, `src/risk/routes.ts` and the legacy audit/approval
routes in `src/index.ts` lack a principal/resource-ownership boundary. An anonymous
caller can list wallets/sessions and request STEP-UP actions or payment transitions.
PayPal buyer approval remains necessary, but it does not authorize the caller to
change IntentLock authority. Financial records and prompts can also be disclosed.

`src/authorize/routes.ts` authenticates API clients and checks scopes;
`src/authorize/service.ts` rejects cross-client token verification. However,
`/v1/authorize` has no client-to-wallet grant model and trusts submitted merchant
and transaction facts. It must not be marketed as a complete commerce enforcement
boundary. TrustOps mutation endpoints require their existing operations token.

No owner field, principal mapping, login system, or blanket API key has been
invented here. Release requires an agreed identity/grant model and cross-principal
tests for wallet grants, session ownership, approval actors and financial reads.
Current tests protect existing API key/scope/token isolation and TrustOps checks;
they do not claim that cross-user wallet isolation exists.

### P1: wallet-wide authority is not reserved before capture

`src/session-payments/service.ts` revalidates each session before capture but has
no atomic wallet-wide pending reservation. Two distinct sessions can both observe
$100 remaining and each request $70 capture before settlement. The SQL wallet
ledger (`db/v11_0_3_late_capture.sql`) prevents a second over-budget debit only
after provider money movement. Provider request idempotency protects retries of
one payment; it does not constrain the sum of distinct payments.

A safe solution needs a persistent reservation lifecycle bound to exact quote,
wallet and provider operation, including ambiguous outcomes, expiry, release,
webhook settlement and reconciliation. A Redis-only lock, post-capture rejection
or runtime configuration flag is not a resolution. Not implemented here.

### P1: PayeeLock is not bound to the payment recipient

`src/commerce/payee-lock.ts` binds structured catalog identity to quote context,
but `src/session-payments/providers/types.ts` does not pass an enforceable recipient
to `createPayPalOrder`, and `providers/paypal.ts` omits a bound payee in the purchase
unit. Enforce-mode catalog registry membership does not prove the actual provider
recipient. Capture verification also does not compare recipient identity.

A safe solution needs a verified mapping from seller identity to the supported
provider recipient, account/platform capabilities, explicit recipient binding,
and provider evidence validation. Configuration alone is insufficient.

### P1: external catalog discovery is not merchant checkout

`src/commerce/shopify-connector.ts` and `ebay-connector.ts` discover/revalidate
listings. The generic PayPal order does not create the corresponding merchant
cart/order, include final shipping/tax commitments, reserve inventory, or prove
fulfillment. A sandbox capture cannot establish purchase of the discovered item.

Keep Shopify Global Catalog MCP discovery-only until exact merchant/offer/variant
identity, final totals, inventory, recipient binding, executable checkout and
verified order/payment events have a defined contract. Do not expose bypass
checkout tools, credentials, or direct agent execution outside IntentLock.

## Remaining limits and required follow-up

- A process crash after claiming discovery leaves SEARCHING non-runnable. There
  is deliberately no unsafe automatic takeover without a lease/recovery protocol.
- STEP-UP request/grant/session state changes are atomic; subsequent explanatory
  event delivery can still fail and needs operational replay/monitoring.
- No scheduled fleet reconciliation or queue dead-letter provisioning is added.
- Legacy `/api/payments/create-link` uses an Intent Contract rather than an Intent
  Wallet and has no wallet/agent risk identity. The new risk parity tests cover
  session execution and `/v1/authorize`, not retrofitted risk enforcement on that
  unscoped legacy rail. Retiring or migrating it needs an explicit contract.
- The legacy Security Lab still depends on an Intent Contract not created by the
  current purchase flow; its UI prerequisite requires a separate product decision.
- This change does not upgrade catalog seller labels into verified merchant facts.
- Browser visual/mobile validation and live provider lifecycle validation remain
  separate from unit/SQL tests, build success and Worker bundling.
- The extra strict Worker TypeScript check still has 15 inherited diagnostics in
  agent decorators, route response typing, Cloudflare Request typing and older
  BufferSource annotations. An in-memory check against unchanged HEAD reproduced
  17 diagnostics; this patch removes the two queue checkout URL diagnostics and
  adds none. The requested Worker bundling check passes independently.

## Validation

The initial regression reproduced 16 failures in malformed input and preflight.
Added suites cover schemas and deterministic policy, SQL lifecycle/STEP-UP races,
authorization consumption/replay, independent receipt tampering, full receipt
verification gates, real entry-point risk parity with isolated repositories,
cross-client token rejection, existing authentication/scope enforcement, CORS
origin/header restrictions, environment propagation, demo selection and frontend
runtime configuration. The final suite has 313 tests across 49 files (98 added
tests in seven new suites, retaining all 215 pre-existing tests). The production
frontend build passes; the Worker dry-run bundles without deployment.

Merge as a scoped hardening change only after automated checks pass and the
remaining blockers are explicitly accepted; this is not approval for public
financial execution or payment-capable Shopify MCP integration.
