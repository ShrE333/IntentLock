  tests reset isolated quotas/resources between independent cases. This does not

  are blocked; no buyer approval, capture or refund is available in these tests.
- Extended the full-schema HTTP integration tests through actual PayPal adapter
  code with intercepted OAuth/order/authorization/capture/verification/read responses.
  Capture alone leaves the spent ledger empty. Mock-authenticated webhook settlement
  produces a real HMAC/audit/recipient-verified receipt. Duplicate delivery leaves

  retains RECONCILIATION_REQUIRED authority, then recovers through the verified
  webhook without a second capture request. Provider signature-verification responses
  are mocked; this is not proof of live PayPal webhook authenticity.
- Fixed the homepage policy runner's dependency on configured payment services.
  Visitors can now run ALLOW/STEP-UP/BLOCK using the deterministic catalog while
  payment unavailability is explicit. Backend payment/recipient/reservation gates
  remain unchanged. Missing credentials do not fabricate payment readiness.
- Wallet loading now differs from an empty account. Changed the purchase result
  label from VERIFIED PURCHASE to VERIFIED PAYMENT, commerce configuration status
  from CONNECTED to CONFIGURED, and removed an unconditional WhatsApp claim that
  the deployed web flow is functioning.
- Mobile traces reproduced repeated pointer interception. Viewport diagnostics
  showed the mobile grid expanded to navigation min-content width (1322px), causing
  a panned visual viewport. Constrained the mobile column with minmax(0,1fr) and
  sidebar min-width:0. Strengthened overflow assertions to compare scrollWidth with
  clientWidth rather than innerWidth, which Chrome can expand with overflow.
- Added Playwright CI installation/execution before the final production build;
  retained strict checks, repeated unit tests, PostgreSQL validation and dry-run.

## Controlled PayPal Sandbox validation plan — NOT EXECUTED

1. **Configuration sign-off:** use a dedicated nonproduction database and isolated
   deployed sandbox stack. Confirm reviewed .4 -> .5 -> .6 migrations after their
   prerequisites, all consumer versions, trusted HTTPS frontend/Worker origins,
   CORS, queue delivery/recovery ownership and server-only credentials. Review
   advisories before exposing the test stack. Never roll back to old financial writers.
2. **Merchant:** independently verify the actual receiving sandbox business account's
   exact merchant ID and legal/operator control. Verify that the OAuth application's
   credentials belong to that account. Neither catalog seller text nor synthetic
   test IDs establish identity. Record nonsecret operator sign-off evidence.
3. **Mapping:** independently approve the exact environment/connector/provider/seller
   mapping, merchant-of-record and checkout merchant. Use DIRECT_MERCHANT, a current
   mapping version/expiry and an approval reference. Confirm expected receiving ID
   equals PAYPAL_ACCOUNT_MERCHANT_ID. Do not create fictional onboarding evidence or
   production mappings. Obtain a fresh quote after mapping changes.
4. **Buyer:** prepare a separate sandbox personal buyer account and test funds,
   compatible buyer/account countries and presentment currency; do not use real card
   details or production credentials. The operator handles account authentication.
5. **Permissions:** verify sandbox OAuth token acquisition, Orders AUTHORIZE and
   authorization/capture read/write eligibility for the controlled receiving account.
   Third-party partner routing is unsupported; merchant assertions/platform permission
   requirements cannot be replaced by setting a merchant ID.
6. **Webhook:** register the exact HTTPS Worker URL and sandbox app webhook ID;
   verify required transmission headers/raw body and PayPal verification success.
   Confirm rejection of missing/invalid signatures, exact order/auth/capture/session,
   currency/amount/payee matching and unknown-event quarantine. Mock SUCCESS is not
   acceptable as live validation evidence.
7. **One transaction, only after separate authorization:** fresh visitor -> $100
   USD wallet -> Sony $49 discovery -> policy ALLOW -> durable $49 reservation ->
   order with expected payee -> buyer approval -> authorization -> fresh recipient,
   quote/risk/wallet checks -> capture. Capture response must leave settlement pending.
   Verified webhook must produce exactly one $49 spent entry, zero held authority and
   a complete independently verified receipt. Record sandbox/test-funds labeling and
   explicitly state that no external merchant fulfillment order was created.
8. **Receipt:** authenticated proof read must recompute canonical payload hash and
   server-side HMAC, verify audit/evidence head/identity and persisted recipient graph.
   Do not export signing secrets to judges or browser code. Demonstrate a failing
   local tamper case using disposable test evidence, never by editing a real receipt.
9. **Replay:** use an approved provider redelivery mechanism or authorized evidence
   replay through existing server recovery. New raw requests need authentic provider
   verification; do not synthesize a valid signature. Confirm unchanged ledger count,
   spent total and receipt identity. Preserve raw observations for investigation.
10. **Interrupted capture:** under a reviewed test fault plan, interrupt the response
    after dispatch without reissuing capture. The hold must remain conservative.
    Use verified webhook or authenticated server reconciliation of provider truth;
    missing/conflicting IDs retain the hold. Do not release on timeout or automatically
    void/refund. Record final provider IDs, reservation state, ledger count and proof.

The current instruction does not authorize steps 7–10 against PayPal. This plan is
reviewable preparation, not approval or a claim those steps succeeded.
HMAC is a server-verifiable integrity mechanism, not a public-key signature. Judges
can inspect the canonical hash/audit evidence and authenticated verification result;
they cannot independently verify HMAC offline without the signing key, which must
not be disclosed. Public offline verification would require a separately designed
asymmetric signing/key-publication scheme; none is claimed here.

## Judge-mode checklist and three-minute script

Before presenting: install dependencies/browser; run the documented local tests;
use fresh browser contexts; make mock versus real environment unmistakable; have
test counts/trace/report available; ensure no administrative token or signing key
is visible. Never present a fixture mapping or mocked webhook as PayPal evidence.
For an interactive no-payment rehearsal, start the Worker fixture with
`npm --workspace apps/worker exec -- vitest run --config browser/vitest.config.ts`.
In another PowerShell terminal, set
`$env:NEXT_PUBLIC_INTENTLOCK_API_URL='http://127.0.0.1:18747'`, then run
`npm --workspace apps/web run dev -- --hostname 127.0.0.1 --port 18748`.
Open `http://127.0.0.1:18748`. The fixture is temporary (ten-minute ceiling),
loopback-only, uses disposable PGlite and has payments unavailable. Stop both
processes after rehearsal. Never deploy the fixture or its reset endpoint.
Production demo limits remain USD <=$100, short-lived capability, constrained wallet
expiry, two wallets/principal/hour, three capability issuances/IP/hour and mutation
quotas. Multiple judges behind one NAT can hit issuance limits; preflight the plan
without relaxing authorization or silently sharing a principal. A new session loses
access to previous anonymous resources; operators retain historical recovery.

- **0:00–0:25:** “An agent recommends; a deterministic firewall grants authority.”
  Explain the wallet is spending permission, not deposited money. State sandbox
  versus isolated mock status before showing anything.
- **0:25–1:00:** fresh visitor creates the $100 scenario wallet. Run Sony; show actual
  ALLOW and the bound candidate. Explain durable reservation precedes financial
  dispatch; policy ALLOW alone is not a payment.
- **1:00–1:40:** run Bose, show exact-quote STEP-UP and Allow Once; run Boat, show
  BLOCK. Do not click payment checkout during this no-payment demonstration.
- **1:40–2:10:** open a second browser context; its wallet list is empty and a copied
  foreign session is denied. Show pending/missing proof without a VERIFIED badge.
- **2:10–2:45:** show the isolated PostgreSQL integration test evidence: authorization,
  capture response, verified-mock webhook, one ledger entry and real HMAC/audit proof;
  duplicate replay and interrupted response recover once. Explicitly call these
  intercepted provider responses, not an actual PayPal transaction.
- **2:45–3:00:** explain the separately gated controlled sandbox plan. Shopify is
  discovery-only, no external merchant order/fulfillment is claimed, and actual
  provider/account checks remain outstanding.

Once separately authorized live sandbox evidence exists, replace the test-evidence
segment with that exact owner-accessible sandbox receipt and provider transaction;
do not invent or alter historical evidence for the presentation.
