# V11.4.5 — Atomic Wallet Authority Reservations

## Scope and result

This adds durable wallet authority reservations to the existing V11.4.4 ownership
boundary and V11.4.3 financial state checks. The previous race was real: separate
sessions could both pass checks against settled spend and request captures before
either webhook debited the wallet. Payment-record uniqueness and Redis locks
protected one session, not the sum of different sessions.

New execution reserves wallet authority before creating either provider's checkout.
The database serializes contenders on the wallet row, records provider dispatch
before the network call, and transfers reserved authority into spent authority in
the same transaction as the unique ledger insertion. A timeout does not free funds.

The migration has **not** been applied outside isolated PGlite tests. No provider
payment, authorization, capture, refund, checkout, production migration, deployment,
commit or push was executed. Provider behavior in regression tests is mocked.

## Authority invariant and serialization

For each wallet:

```text
active_reserved = SUM(amount WHERE state IN (RESERVED, RECONCILIATION_REQUIRED))
available       = total_authority - spent_amount - active_reserved
spent_amount + active_reserved + requested <= total_authority
```

`intent_wallets.reserved_amount` is the database-managed aggregate. Each reservation
creation/transition updates it through a trigger. A wallet check constraint enforces
nonnegative reservations and `spent_amount + reserved_amount <= total_authority`.
Direct application updates to the counter are rejected. Currency changes are
rejected once a wallet has reserved or spent funds.

The SQL functions acquire `SELECT ... FOR UPDATE` on the wallet before inspecting
or changing reservation state. Every contender therefore reads the current locked
wallet counter. This avoids relying on a possibly stale MVCC snapshot of a SUM
after waiting for another transaction. There is no Redis or process-local authority
lock. The existing Redis checkout lock remains an optimization only.

One session has one immutable reservation UUID and operation key. Wallet, session,
amount, currency, quote hash, provider, deadline and operation key cannot be
reassigned. Same-session retries return the existing matching reservation without
adding authority. Conflicting retries fail. Different sessions compete for the same
counter. Provider order/authorization/capture identities are unique within their provider;
the ledger also has a unique provider/capture index and retains session uniqueness.

Amounts remain PostgreSQL NUMERIC throughout authority arithmetic. The reservation
uses `authorizationContext.walletAmount/walletCurrency`, never a smaller merchant
presentment amount. The SQL boundary checks the stored selected-product context,
wallet currency, positive finite amount, currency precision and hard ceiling.
The existing wallet/ledger columns are NUMERIC(14,2): amounts needing a third
decimal are rejected, rather than rounded into those columns. Supporting true
three-decimal money requires a separate end-to-end storage/provider change.

## State machine

| From | To | Required evidence or condition |
| --- | --- | --- |
| No row | RESERVED, phase NONE | Active/unexpired wallet, matching session and quote, sufficient locked authority |
| RESERVED | RECONCILIATION_REQUIRED | Atomic admission of one CHECKOUT, AUTHORIZE or CAPTURE operation before network dispatch |
| RECONCILIATION_REQUIRED | RESERVED | Matching successful provider response, or independently fetched authorization recovery facts |
| RESERVED / RECONCILIATION_REQUIRED | COMMITTED | Exact independently verified settlement evidence and matching unique ledger, one transaction |
| RESERVED, phase NONE | RELEASED | Known pre-dispatch failure; no provider operation has started |
| RESERVED | EXPIRED | Deadline passed and phase NONE, or confirmed PayPal checkout that never began authorization |
| RESERVED, phase AUTHORIZE | RELEASED | Authenticated provider reads prove the bound authorization VOIDED/EXPIRED, with no order captures |
| RESERVED / RECONCILIATION_REQUIRED, phase CAPTURE | RELEASED | Exact persisted, signature-verified terminal PAYMENT.CAPTURE.DENIED evidence |
| COMMITTED / RELEASED / EXPIRED | Terminal | Cannot be resurrected, resized, reparented or moved to another state |

The trigger enforces the allowed transitions and requires a matching ledger before
COMMITTED. Financially exposed releases require persisted release evidence.
Reservation transition events are append-only operational history; they do not
replace the existing HMAC receipt or hash-chained session audit.

Phase is monotonic: NONE → CHECKOUT → AUTHORIZE → CAPTURE for PayPal, and NONE →
CHECKOUT for Razorpay. A caller cannot replay an operation by changing phase back.
RECONCILIATION_REQUIRED counts fully against authority, even after its deadline.
It is set before dispatch, rather than optimistically guessing an error was safe.

## Execution boundaries

The conservative reservation boundary is **before checkout creation**. A Razorpay
link can accept asynchronous payment without another IntentLock call. PayPal creates
AUTHORIZE orders; reserving before creation also gives its approval/hold/capture
sequence one immutable authority identity. This intentionally trades some temporary
availability for a uniform fail-closed boundary.

1. Reload the stored session/wallet; re-read catalog availability, quote, bound
   catalog payee facts, country and FX freshness/drift. Recompute the bound quote.
2. Run deterministic policy and the shared adaptive risk tightening engine. Risk
   can only tighten the result. BLOCK stops execution; STEP-UP requires the existing
   approved, unexpired, quote-bound one-time authorization before financial execution.
3. Reserve the exact wallet amount under the wallet lock before creating the
   payment record/provider object. Missing schema, SQL error or insufficient
   authority stops before any provider call.
4. Durably mark CHECKOUT dispatch; create checkout with its existing idempotency key;
   persist the provider order and confirm the operation.
5. After buyer approval, revalidate commerce, quote, policy, risk and approval.
   Consume required one-time authority, then atomically admit AUTHORIZE at the
   reservation boundary before requesting the provider hold.
6. Revalidate again after authorization and immediately before capture. Under the
   wallet lock, check wallet status/validity, reservation deadline/currency, current
   hard ceiling and current auto-buy/consumed approval requirements. Admit CAPTURE
   before calling PayPal. An expired/revoked wallet cannot dispatch new execution.
7. A successful capture API response records the capture ID only. It does not debit
   the wallet, create a verified receipt or claim settled payment.

Approval consumption and reservation admission are separate durable checks under
their existing database locks, not one combined SQL statement. Either failure stops
provider execution. Once authorization might exist, a later capture admission error
does not recycle its consumed grant. Checkout returns a consumed grant only after
the database successfully releases a still-unexposed reservation; a losing concurrent
caller cannot return the winning caller's grant.

The reservation deadline is the earlier of wallet expiry and 20 minutes after
reservation. A wallet/policy change can prevent further dispatch, but never erases
an already exercised financial obligation. Existing grants cannot increase total
authority through this layer.

## Verified settlement and replay

The new settlement function validates the stored session/wallet/payment/quote/key,
provider order/authorization/capture IDs, wallet-currency amount, and persisted
provider webhook evidence. PayPal completion must carry the exact completed capture
resource. Razorpay completion must carry the exact captured payment amount/currency
and link. Authentication remains independent of visitor ownership/capability TTL.

One SQL transaction inserts the unique ledger row, marks the reservation COMMITTED
(subtracting it from the reserved counter), and increments spent. Other transactions
cannot observe an intermediate transfer. Any failed check rolls everything back.
Concurrent/replayed deliveries return the existing matching debit and cannot count
the same money twice. Current expiry/revocation does not discard a valid, previously
admitted reserved capture; it still settles exactly once.

Session completion, hash-chained audit events and the immutable signed proof receipt
follow the durable ledger transfer. Failure after transfer remains retryable and
does not repeat the debit. Existing receipt hashing, independent HMAC verification,
audit verification and first-receipt immutability are unchanged. A late denial cannot
release a COMMITTED reservation or downgrade a completed payment.

Razorpay now also retries paid-webhook settlement if a prior delivery was received
but settlement failed. A receipt of a webhook is not treated as proof of settlement.

## Recovery and availability limits

The existing operator-only reconciliation endpoint is retained:
`POST /api/trust-center/reconciliation/:session/reconcile`. It first replays saved
verified PayPal completion evidence. Without it, reservation reconciliation can:

- Expire a never-dispatched reservation or a confirmed, abandoned PayPal approval
  whose authorization never began. New reservations on the wallet also sweep these
  safely expirable rows under the same wallet lock.
- Read the existing PayPal order/authorization through authenticated provider GETs.
  Recover a lost authorization response only when its order, session custom ID,
  amount, currency and authorization identity match. No second authorization is sent.
- Release a confirmed authorization only when those reads prove it terminal and
  uncaptured. A browser cancel redirect is not provider truth.
- Release an exact terminal capture denial from independently verified ingress.

**Deliberate holds:** checkout timeouts without a known provider object, capture
timeouts without verified completion/terminal denial, contradictory provider facts,
and Razorpay failure/cancellation/expiry without adequate terminal truth stay held.
They are not automatically replayed, expired or released. In particular, an error
message or HTTP timeout is not proof of nonpayment. Unknown capture operations are
not retried after a provider idempotency window may have elapsed.

There is no new provider void/refund mutation, automated fleet sweeper, or generalized
provider investigation tool in this patch. Operations must obtain terminal provider
evidence for unresolved holds; unsupported cases remain quarantined. Instrument
reservation age, reserved totals, ambiguous phases, evidence failures, reconciliation
failures and queue/dead-letter retries before enabling production execution.

PayPal documents that a voided authorization cannot be captured or reauthorized:
[PayPal authorization-voided contract](https://developer.paypal.com/api/payments/v2/errors/authorization_voided/).
The provider's published webhook contract distinguishes capture completion and
denial: [PayPal webhook specification](https://github.com/paypal/paypal-rest-api-specifications/blob/main/openapi/notifications_webhooks_v1.json).
These contracts inform the conservative terminal-evidence handling; no live behavior
was demonstrated by this work.

## Ownership and asynchronous execution

V11.4.4's exported Worker access gate still authenticates principals and enforces
stored resource ownership/grants before checkout, authorization, capture, payment
reads and operator reconciliation. There is no public reservation mutation route.
Browser-supplied wallet IDs, principal IDs, reservation states and ownership fields
cannot establish authority. SQL independently requires the session's actual wallet.

Interactive queue jobs retain their stored, verified session/chat binding, pairing
and wallet grant checks. The consumer now also propagates the derived WhatsApp
principal under the private server identity Symbol into execution. Verified provider
settlement jobs retain their separate evidence-only recovery boundary.

The owned payment GET returns reservation facts; the wallet UI distinguishes
reserved authority from available authority. This display does not authorize spending.
Database credentials and provider credentials remain server-side; compromise of those
trusted credentials is outside application ownership checks.

Existing `/v1/authorize` API tokens retain their authenticated policy contract; token
issuance itself does not execute payment or reserve money. The reservation guarantee
covers the managed PurchaseSession provider execution paths. An external agent that
pays outside those paths is outside this enforcement boundary; an ALLOW token must
not be presented as reserved funds or as permission to bypass managed execution.

## Migration, rollout and rollback

Migration: `apps/worker/db/v11_4_5_wallet_reservations.sql`. Apply exactly once using
the normal reviewed schema-version process, after V11.4.4 and its prerequisites.
It runs in a transaction and adds the counter, invariant, reservation/evidence/event
tables, indexes, trigger guards and functions. It does not update financial amounts,
manufacture old reservations, rewrite sessions/payments/receipts, or deduplicate
historical captures. Conflicting historical capture identities fail the migration
and roll back its schema changes.

Required rollout gates:

1. Keep financial mutation ingress and interactive execution queues paused across
   migration/cutover. Drain old invocations. **Mixed old/new execution is unsafe**:
   old application versions do not reserve before provider calls. Independent
   verified settlement recovery must remain available through the controlled cutover.
2. Review outstanding historical provider objects and capture-ID uniqueness without
   exposing secrets. A wallet with any pre-upgrade payment record lacking both a
   reservation and a ledger is quarantined from new reservations, even if its local
   status says FAILED. Local status alone does not prove provider nonpayment.
3. Test on a nonproduction PostgreSQL clone. Use separate simultaneous connections
   to exercise lock waits, rollback, transaction cancellation/deadlocks, duplicate
   webhooks and process loss at each network/SQL boundary. Verify stored counter =
   active-reservation SUM and settled spend = the ledger aggregate.
4. Apply the reviewed migration, verify schema/indexes/functions/invariant, deploy
   all execution consumers consistently, and confirm V11.4.4 ownership/grants remain
   active. No old consumer may initiate provider actions during this interval.
5. Configure reconciliation monitoring/retention and provider event subscriptions;
   exercise controlled provider recovery separately before financial traffic resumes.

New code with old/partial schema fails closed; it does not catch SQL errors and fall
back to unreserved execution. Historical verified PayPal settlement with no reservation
uses the existing V11.0.3 evidence/history function, including its original checks.
Existing ledger recovery remains available after expiry/revocation. Historical
unsettled records are not silently assigned a new reservation, and historical
interactive capture cannot proceed without reserved authority.

Quarantined historical failures without sufficient terminal evidence may prevent
new activity on an old wallet. This is an explicit cutover/recovery gate, not an
automatic data-cleanup task. This patch provides no unsafe override that deletes
those obligations or edits historical records.

Rollback is not a blanket DROP script. Stop new financial actions first, drain
consumers, reconcile active/ambiguous reservations, and preserve ledger, receipts and
transition/evidence history. Keep this schema and settlement-compatible code while
any reserved obligation remains. Do not roll payment execution back to pre-reservation
code. A reviewed schema removal is safe only after no active reservation or in-flight
provider operation remains and historical metadata is archived; it was not executed.

exercise the real payment orchestration with mocked provider/storage boundaries.
Additional exported Worker tests reject cross-user checkout/authorization/capture
before execution, including forged ownership and reservation fields.

Coverage includes two $70 sessions against $100, twenty competing sessions,
same-session retries, twenty settlement replays, provider timeouts, pre-dispatch
release, authorization recovery, terminal denial, abandoned approval expiry,
revocation/expiry, changed limits, STEP-UP resolution races, exact FX reservation,

historical paid rows and migration rollback on duplicate captures. The original

PGlite serializes requests through its embedded database connection. These tests

## Remaining release blockers

- Actual PayPal recipient binding remains unresolved. Catalog PayeeLock stability
  is not evidence that PayPal paid that merchant. Configuration cannot fix this.
- Shopify/eBay discovery remains separate from executable merchant checkout,
  shipping/tax finality, merchant order creation and fulfillment.
- Production concurrency/fault-injection validation, old-consumer cutover,
  historical quarantine review, ambiguous-hold operations, observability and
  reconciliation coverage are mandatory release gates.
- Strict TypeScript baseline diagnostics remain separately tracked. Passing the
  configured frontend build or Worker bundle does not mean strict checks passed.

This is a reviewable reservation implementation, not approval for unrestricted
production payment execution or payment-capable commerce MCP integration.
