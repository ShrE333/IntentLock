# V11.4.4 Financial Access Control and Resource Ownership

## Scope and activation

This is an additive server-side access-control layer over V11.4.3. It does not
implement wallet-wide spending reservations, payment-recipient binding, merchant
checkout, or a verified human/customer account system. Those remain separate
financial architecture requirements. No existing financial record is reassigned.

The migration `apps/worker/db/v11_4_4_financial_access.sql` is required before
activating the new HTTP/interactive-queue code. It has **not** been applied to any
production database. It creates access tables only; it does not update wallets,
sessions, payments, grants from previous versions, audit events, receipts or refunds.
Missing access storage fails closed with 503. Provider webhook settlement and
verified-evidence settlement jobs do not require a browser capability or an owner
backfill, so historical payment recovery remains available.

## Identity model

| Principal | Server evidence | Authority |
| --- | --- | --- |
| `demo:<random UUID>` | 256-bit opaque bearer capability; only SHA-256 hash stored | Fixed sandbox scopes, expiry and quotas; owns resources it creates |
| `api:<verified client ID>` | Existing active API key hash and existing scopes | Requires both an endpoint scope and ownership or a live permission grant |
| `wa:<SHA-256 of chat ID>` | Verified WAHA raw-body HMAC, paired chat and current wallet grant | Only resources granted to that chat; checked again by the queue |
| `ops:trustops` | Existing server-held TrustOps operations credential | Explicit privileged recovery and cross-resource operations |
| `admin:api-key` | Existing server-held API administration credential | Creates/revokes expiring client/chat wallet grants; every change is audited |

No browser ownerId, userId, principalId, channel label, walletId or sessionId is
accepted as identity. IDs identify a requested resource only. Verified identity is
passed internally under a module-private Symbol on a fresh Worker environment;
HTTP JSON/headers cannot create that context. The exported Worker fetch entry
point applies the access gate before dispatching sensitive handlers. Unclassified
routes return 404 by default. Route helpers are internal server functions, not
independent HTTP entry points.

`financial_resource_owners` records immutable application ownership for new
wallets and legacy intents. Wallet creation and owner insertion share one SQL
statement: an ownership failure rolls back the wallet too. Parser-generated intent
IDs receive the authenticated principal in the same statement as persistence.
Operator-created resources can remain unassigned until explicit delegation.

Sessions inherit their wallet's access. Payments, one-time authorization grants,
session audit events, proofs, refunds and evidence inherit through their stored
session/wallet relationships; no client-supplied owner field can reparent them.
Legacy audit streams use the persisted intent owner. Nested STEP-UP request IDs
must also resolve to the wallet in the path before their handler is invoked.

Owner access is intersected with endpoint scopes. Delegates additionally require
`read`, `authorize`, `execute`, or `approve` as appropriate. Grants expire and can
be revoked. Resource mutations that return financial facts also require read;
an execute/approve/authorize-only delegation is insufficient to expose those
facts. API authorization requires both read and authorize. List filtering occurs
in SQL **before** ordering/LIMIT. Foreign and
missing resources return the same 404 response. Missing/expired credentials return
401, scope/privilege violations 403, quotas 429, nonce replay 409, oversized JSON
413, and unavailable access storage 503. Sensitive responses use Cache-Control:
no-store. CORS only controls browser transport and is not authentication.

## Anonymous sandbox capabilities

- `POST /api/access/demo` needs no external account or signup. Each issuance gets
  a new principal and a cryptographically random `ildemo_` bearer token, valid for
  30 minutes. There is no global browser credential and no signing secret is added.
- `POST /api/access/refresh` requires a currently valid demo token and atomically
  revokes it while issuing a new token for the **same** principal. Replaying the
  revoked token cannot refresh again. Expired capabilities cannot be refreshed.
- `POST /api/access/logout` revokes the capability. A new visitor session cannot
  claim the old visitor's resource IDs. Old financial evidence is retained.
- Token responses carry fixed public scopes, never administrative scopes. Server
  authorization uses its fixed scope set, not scopes supplied by the browser.
- The frontend stores the token in sessionStorage, retains it across same-tab
  PayPal returns, deduplicates concurrent bootstrap/refresh requests, and rotates
  before expiry. Tokens never appear in links or return URLs. Expiry is explicit;
  the user can start a new sandbox session rather than silently claiming old work.
- New/reset sessions isolate capability holders. A copied/stolen bearer token is
  possession of the same principal, not proof of a different named human. A shared
  browser must be reset between visitors. This is a capability demo, not KYC/login.
- Capabilities work only with DEMO_ACCESS_ENABLED=true and sandbox PAYPAL_ENV.
  The request's effective payment rail is restricted to PayPal sandbox. Session
  creation/search require the deterministic sandbox connector; existing session
  access also checks the stored connector and USD wallet. Browser labels cannot
  turn a live or external merchant session into a sandbox session.
- Demo wallets are USD, at most $100 delegated authority and at most 24 hours of
  wallet validity. Existing numeric/hierarchy checks still apply. Each principal
  may create two wallets/hour and each trusted ingress IP six/hour.
- Issuance: three capabilities/IP/hour, 200 total/hour. Authenticated requests:
  60/principal/minute; protected ingress: 120/IP/minute; demo mutations: ten/minute;
  Workers AI parsing: three/principal/hour. Counters are atomic database upserts.
  Refresh preserves the principal, so it does not reset its mutation/wallet limits.
- IP keys are hashed and never returned. CF-Connecting-IP is trusted only at the
  Cloudflare ingress; a directly exposed development origin must not be treated
  as a trusted public deployment. Missing IP uses one conservative shared bucket.
  Global issuance quotas remain even if client IPs vary. Edge WAF/DDoS controls
  are still required for volumetric traffic before database authentication.
- Demo mutations require a fresh x-intentlock-request-id, atomically claimed per
  principal. Duplicate request IDs are rejected before handler execution. Ordinary
  bearer reuse for reads is intentional; possession still authorizes until token
  expiry, rotation or logout. Financial idempotency remains independently required.
- Request JSON is bounded to 16 KiB. Rate/nonce enforcement fails closed on storage
  failure. Financial mutations are not automatically retried by the browser after
  ambiguous network outcomes; inspect the stored session instead.

The public frontend no longer accepts a TrustOps admin token. Refund execution,
provider synchronization, deep provider scans and administrative reconciliation
require a separate authenticated **server-side** operator integration. Demo users
can inspect their own evidence and evaluate refund policy without executing a
refund. API integrations continue to use their existing API keys, never demo tokens.

## API integration and historical recovery migration

Existing API keys, client IDs, token formats, scopes authorize/verify and provider
idempotency keys are retained. Existing keys do **not** automatically acquire every
historical wallet: that unrestricted behavior was the defect. Before switching an
integration, an operator must explicitly grant its verified client the correct
wallets through the authenticated administration endpoint. Minimum authorization
integration permissions are read/authorize; execution and approval are separate.
Additional HTTP endpoint scopes require explicit administrative provisioning.

The grant request identifies exactly one existing active clientId or paired chatId,
walletId, permissions and optional expiresAt (one hour default, 90-day maximum).
The server derives api:/wa: principal IDs itself; submitted owner/principal fields
do not grant authority. Revocation and grant changes are audited atomically with
their access-row update. No browser-side administrative credential is introduced.

Do not infer ownership from old browser IDs, public wallet lists, historical
authorization requests, or WhatsApp active-wallet selections. These were formerly
untrusted inputs. Unassigned historical resources remain visible to authenticated
operators, and can be delegated after independent business verification. There is
no public claim-by-ID or claim-by-first-access endpoint.

Provider webhooks still bind order/authorization/capture evidence to persisted
payment/session/wallet rows and settle exactly once. FINALIZE_PAYPAL_CAPTURE jobs
reload persisted verified evidence; they do not depend on visitor capability TTL.
Operators can run the existing evidence-gated reconciliation path for old records.
Ownership grants never substitute for a verified webhook, approval token, quote,
wallet policy, HMAC, or receipt integrity check.

## WhatsApp and queue trust boundary

WAHA authenticates the exact raw request first, checks pairing and deduplicates
messages as before. Paired chats now see only explicitly granted wallets. Old
active-wallet/session selections are rechecked before read, BUY or STEP-UP actions.
Pairing grants channel access, not global wallet authority.

Interactive queue messages include an opaque jobId issued by the authenticated
server. The database record binds job kind, session, chat principal, chat reply
destination, WAHA session and a 30-minute execution deadline. Queue consumers
recheck current pairing and wallet execute permission and claim a short lease
before any discovery/payment work or reply. Forged/unregistered jobs cannot pick
an arbitrary session or reply destination. DONE jobs are not executed again.

Historical interactive messages without a trusted job record cannot initiate new
payments. They must be reissued through an authenticated, explicitly authorized
chat/operator path. This is distinct from historical payment **settlement**, whose
verified-evidence jobs remain independently recoverable. A crashed discovery still
requires the V11.4.3 state-integrity recovery policy; this change does not invent
unsafe takeover of SEARCHING sessions or exactly-once provider execution.

## Threat model and limits

Protected against: anonymous financial enumeration/mutation, IDOR across demo
visitors/API clients/chats, forged ownership/scope fields, use of revoked/expired
capabilities or grants, mutation request-ID replay, browser admin escalation,
queue-message identity substitution and anonymous Durable Object state access.

Trusted: Cloudflare Worker runtime, backend database and credentials, the existing
administrative/TrustOps credential holders, WAHA/provider signature mechanisms and
verified API-client provisioning. The database credential remains server-side;
this is application enforcement, not a claim of PostgreSQL row-level security.
Compromise of a backend credential or an XSS that steals a still-valid bearer
capability is outside what resource-ID checks alone can prevent. Use HTTPS, protect
the frontend origin, restrict CORS where appropriate, and keep admin credentials
out of the browser. Browser automation/mobile behavior still needs separate QA.

Checks establish authorization at request admission and queue consumption, not a
transactional reservation across provider network calls. Revocation cannot undo
an already accepted provider operation. The pre-capture aggregate reservation
race and PayPal recipient-binding defect remain unresolved. External Shopify/eBay
discovery still does not create a merchant order or prove fulfillment.

Expired capability/rate/nonce/job rows require periodic operator-managed retention
cleanup. Retain nonce rows at least through their stated expiry (longer retention
is safer); request IDs and bearer revocation do not replace financial idempotency.
Do not delete ownership/grant/audit metadata as a shortcut to assigning ownership.
No cleanup schedule, migration application or production backfill is run here.
