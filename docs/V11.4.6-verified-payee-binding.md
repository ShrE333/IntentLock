# V11.4.6 — Verified Payee & Merchant Binding

## Result and supported scope

V11.4.5 reserved wallet authority but its PayPal order omitted `purchase_units.payee`.
PayeeLock fingerprinted a catalog identity; neither that fingerprint nor a completed
capture response established who received money. The new boundary binds an explicitly
approved recipient into the quote, payment record, provider order, provider evidence,
database settlement admission and signed receipt.

The supported executable path is deliberately narrow: a controlled sandbox catalog
and a server-approved **first-party PayPal sandbox merchant**. The implementation
supports separate sandbox/live registry identities, but does not enable production
demo charges or third-party merchant routing. Shopify, eBay, HTTP catalogs and future
MCP discovery connectors cannot initiate an independent PayPal charge. They remain
available for discovery and deterministic wallet policy evaluation.

No production configuration or merchant mapping was invented, installed or seeded.
Tests use explicitly synthetic merchant IDs and isolated approval references; they
are not onboarding evidence and must never become deployment configuration.

## Provider contracts inspected

- [PayPal Orders v2 schema](https://developer.paypal.com/api/orders/v2/schema.json):
  purchase-unit payee, exact merchant account identifier, order retrieval,
  authorization/capture relationships and full-response preference.
- [PayPal Payments v2 schema](https://developer.paypal.com/api/payments/v2/schema.json):
  authorization/capture resources, linked IDs, amount/currency and webhook contracts.
- [PayPal partner authorize/capture guide](https://developer.paypal.com/platforms/checkout/standard/customize/auth-capture/):
  explicit end-receiver selection and partner/onboarding requirements.
- [PayPal request authentication](https://developer.paypal.com/api/make-api-requests):
  third-party calls require the applicable merchant assertion and platform attribution.
- [Merchant onboarding status](https://developer.paypal.com/platforms/checkout/save-payment-methods/onboarding/platform/):
  server verification of merchant eligibility and granted permissions.

The authoritative recipient is the order purchase unit's exact `payee.merchant_id`.
Authorization/capture resources are not assumed to always carry an independent payee
field. Their IDs, amounts, currencies and order relationships must match that order;
any payee field they do carry must agree. Email and display names are not identity.
Missing order merchant ID, incomplete relationships, contradictory payees or unknown
provider state fail closed. This implementation accepts one purchase unit; multi-unit
or split-recipient checkout needs a separate allocation and settlement design.

## Actual trust model

| Identity | Meaning | Trust source |
| --- | --- | --- |
| Catalog seller | Structured catalog provider/seller ID, separate from display text | Server-selected connector plus exact registry key; external discovery is not checkout authority |
| Merchant of record | Business/legal entity designated for the controlled checkout | Operator-reviewed mapping, not inferred from a brand or seller name |
| Checkout merchant | Entity operating the supported checkout | Explicit mapping; external merchant checkout is not implemented |
| Payment recipient | Exact PayPal receiving merchant account | Approved mapping **and** authenticated provider evidence |

Server-only registry inputs:

- `PAYPAL_ACCOUNT_MERCHANT_ID`: operator-verified first-party credential-account ID.
- `PAYPAL_MERCHANT_BINDINGS_JSON`: reviewed exact mappings. Each entry has mappingId,
  mappingVersion, environment, connectorId, catalogProvider, catalogSellerId,
  merchantOfRecordId, checkoutMerchantId, paypalMerchantId, integration,
  approvalReference and validUntil.
- `PAYPAL_ENV`: exact sandbox or live environment; invalid values are rejected.

Merchant IDs follow PayPal's exact 13-character account identifier format. Mapping
keys are exact and duplicate keys fail closed. An entry expires; changing it changes
the quote fingerprint and requires fresh authorization. The receiving ID must equal
the configured first-party account. There is no merchant self-enrollment endpoint,
browser admin credential, merchant-name fallback, email fallback, or observe-mode
bypass. Browser-supplied payees/ownership/approval declarations cannot register trust.

The registry is a server/operator business trust decision, not automatic verification
of a legal entity or PayPal onboarding. Provider GETs independently verify the actual
payment recipient. Deployment operators must independently establish account ownership
and the business relationship before approving a mapping. A configuration string is
not proof of PayPal platform permission.

`PARTNER_ONBOARDED` declarations are explicitly rejected for execution. This patch
does not implement Partner Referrals, merchant consent/status verification, delegated
credential custody, PayPal-Auth-Assertion or platform attribution provisioning.
Approved partner capabilities and seller permissions must be established and tested
before implementing any such path; a registry label cannot substitute for them.

## Quote and execution binding

New authorization contexts can contain `recipient`, with a versioned fingerprint of
all approved mapping fields. It is resolved from a trusted connector ID and exact
structured catalog source, never merchant prose. The fingerprint is included in
future canonical wallet transactions and STEP-UP quote hashes. Absent optional keys
are omitted from historical serialization, preserving old quote hashes.

Discovery may return a policy result without a recipient mapping. **Policy ALLOW is
not executable checkout authority.** Managed PayPal execution requires a bound,
currently approved mapping. All executable commerce is restricted in code to the
controlled demo connectors in sandbox. Adding a mapping for Shopify or renaming
merchant text cannot enable an external charge.

Execution sequence:

1. Revalidate catalog, amount, wallet currency, FX, catalog identity, deterministic
   policy and risk. Check the approved recipient mapping and connector capability.
2. Reserve exact wallet-currency authority using V11.4.5. Persist the expected
   recipient with the payment before provider dispatch. The database requires it
   to match the stored selected-product authorization context and prevents mutation.
3. Create an AUTHORIZE order with `purchase_units[0].payee.merchant_id` set to the
   approved receiving ID. Preserve the API response, then fetch authoritative order
   details. Do not return approval readiness until recipient evidence passes SQL.
4. Before authorization, GET the order again: it must be buyer-approved, have the
   exact expected recipient/session/amount/currency and contain no unexpected prior
   authorization/capture. Require fresh verified evidence at reservation admission.
5. After authorization, fetch order and authorization facts and verify their exact
   relationship before marking the authorization accepted locally.
6. Immediately before capture, repeat order/authorization and mapping checks, while
   preserving wallet validity, risk, STEP-UP and reservation admission rules.
7. Capture the exact bound presentment amount with `final_capture:true`. Preserve
   the response before checking required fields or interpreting an error. Fetch the
   order/authorization/capture graph again. API success alone never settles money.
8. Settle only after independently verified webhook evidence and a matching
   SQL-verified recipient observation. Existing unique ledger/debit and reservation
   transfer guarantees remain in the same transaction.

`Prefer: return=representation` is used for PayPal mutations, but the implementation
still performs provider reads. Read helpers use fixed PayPal hosts and ID-based paths,
not arbitrary webhook/caller-provided links. OAuth token material is never stored in
recipient observations or returned to the browser.

## Evidence, settlement, ambiguity and recovery

`paypal_recipient_observations` stores raw order/authorization/capture facts, API
response bodies and, for settlement, the signed webhook event reference. Records are
initially unverified. SQL independently checks the graph against the immutable
payment expectation before allowing the verified flag. Verified snapshots cannot be
edited, and evidence rows cannot be deleted through ordinary application writes.

The verifier requires order intent/status, one purchase unit, exact session reference
and custom ID, expected merchant ID, amount/currency, correct authorization/capture
membership and related IDs. Settlement additionally requires the exact persisted,
signature-verified completion event and completed capture. Contradictory recipient
fields in either POST responses, GETs or webhooks are rejected.

Signed mismatched events are retained before business validation. Unmatched signed
events are stored with no session assignment; this is evidence retention, not resource
ownership or authority. Invalid signatures do not become verified evidence. Public
API reads never expose the raw observation table or global unassigned deliveries.

On recipient mismatch or failed provider reads, active reservations become
RECONCILIATION_REQUIRED and still count against authority. The code does not mark
the session trusted CAPTURED, debit on insufficient evidence, create a verified proof,
return the consumed grant, refund or void automatically. An already committed
historical capture is never reversed or rewritten by a later contradictory event.

The existing operator-only reconciliation endpoint retains its authentication and
ownership model. It can recover a known checkout after a failed provider read by
verifying the same order, recover an existing authorization using provider truth,
and replay verified settlement. Recovery, terminal denial release and void/expiry
release require recipient evidence where applicable. Unknown provider object IDs,
contradictions and insufficient terminal evidence remain held for investigation.
No fresh charge, automatic refund or automatic void is issued by reconciliation.

Provider network calls cannot share a transaction with PostgreSQL. Verification
occurs at admission and again at settlement; later contradictions are quarantined.
Provider event ordering, read visibility and required field availability still need
controlled real integration testing. Additional GETs/evidence writes also require
Cloudflare subrequest-budget and operational capacity validation.

An explicit different merchant ID is a persistent contradiction, derived in SQL
from the raw evidence. Later matching observations do not clear it or authorize
capture, settlement, recovery or release. There is no client/operator toggle that
disables this guard. Such cases require separately reviewed provider investigation
and an authorized remediation design. Incomplete/read-failure observations can be
resolved by later complete provider truth; this does not erase the earlier evidence.
Proof reads retain the original signed payload but withhold current recipient
assurance when contradictory recipient evidence exists, including after a debit.

## Proofs and sandbox honesty

New PayPal receipts use proof v1.4 and sign the complete expected mapping, actual
merchant ID, environment, sandbox marker and immutable evidence reference. Receipt
reads independently check HMAC, canonical hash, audit chain, receipt identity and
the complete independently persisted recipient mapping/payment IDs.

Historical receipts are not rewritten or re-signed. `integrityVerified` can remain
true for a valid old receipt while `recipientVerified` and overall PayPal `verified`
are false. The UI labels that distinction instead of treating recipient uncertainty
as a new verified purchase. New receipts require recipient evidence; an unbound
legacy capture cannot mint new recipient assurance from configuration alone.

The sandbox runner now also requires recipient mapping configuration. Missing mapping
disables payment availability honestly; it does not install a fake default merchant.
Receipt UI says sandbox payment/test funds and explicitly does not claim a merchant
checkout order or fulfillment. Catalog identity milestones no longer imply verified
payment recipient identity. No actual sandbox approval/capture flow was run here.

## Ownership and external integrations

V11.4.4 authentication, demo capabilities, scopes, wallet grants, queue identities and
operator authentication remain in place. Expected identity comes from stored server
context, not request bodies. Foreign-user payment and merchant-override attempts are
rejected before financial execution. Provider webhook authenticity remains a separate
trust boundary from browser/demo authentication.

The registry is not a Shopify Global Catalog MCP checkout adapter. Discovery,
availability and wallet policy can continue, but shipping/tax finality, inventory
commitment, merchant order creation, delegated checkout and fulfillment are absent.
No generic MCP execution tool or credentials were added. Future tools must use the
managed policy/reservation/payment boundary and an authenticated merchant checkout
contract; catalog metadata cannot authorize a separate PayPal charge.

Existing `/v1/authorize` tokens remain policy authorization contracts, not claims of
reserved money, verified receiving account or a completed merchant checkout.

## Migration, deployment and rollback gates

Migration: `apps/worker/db/v11_4_6_verified_recipient.sql`, after V11.4.4/V11.4.5 and
their prerequisites. It is transactional and versioned for one application. It adds
a nullable payment expectation, observation storage, immutable-evidence guards and
recipient gates around the V11.4.5 SQL admission/settlement/recovery functions. The
prior implementations remain internal helpers. No production migration was applied.

There are no mapping seeds, financial updates, receipt rewrites or historical payee
backfills. Existing records retain NULL expectations. Historical completed records
and matching ledger recovery remain readable/auditable. Unsettled historical holds
without a bound recipient require operator investigation; new code does not continue
their capture or silently promote their catalog identity to payment identity.

Before activation:

1. Freeze new financial mutations, drain old invocations and coordinate queue/schema
   cutover. Retain controlled verified settlement investigation/recovery.
2. Review old pending/ambiguous payments; never fill recipient fields from browser
   IDs, merchant text, an old receipt's catalog seller or a desired outcome.
3. Apply the reviewed migration to a nonproduction PostgreSQL clone. Validate role
   permissions, concurrency, evidence immutability and fault recovery. Database
   credentials and internal helper functions must not be exposed to clients.
4. Independently verify the controlled sandbox merchant account and credential
   ownership, then install exact reviewed server registry entries. Do not copy test
   fixtures. Rotate mapping versions when identities change; obtain fresh quotes.
5. Deploy all consumers consistently. Missing/partial schema fails closed; no SQL
   error is caught as permission for unbound execution. Validate API scopes, raw
   webhook signatures and environment separation before enabling sandbox traffic.
6. Exercise a separately authorized controlled sandbox flow and field contracts,
   webhook replay, timeouts, PostgreSQL concurrency and Cloudflare queue/budget limits.
   Mocked checks are not proof of PayPal account permissions or live end-to-end success.

Rollback is operational, not a blanket DROP script. Stop new financial actions,
drain/reconcile obligations, retain raw evidence/receipts/ledger/reservations, and
keep settlement-compatible guards while any obligations remain. Do not reactivate
pre-binding payment execution. Only remove schema/helpers through a separately
reviewed plan after recovery and archival; no rollback was executed here.
