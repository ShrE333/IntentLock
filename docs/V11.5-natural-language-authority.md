# V11.5 — Natural-Language Intent Wallet Authority Compiler

## Scope and release decision

Implemented an opt-in deterministic natural-language compiler, editable policy
review, hypothetical simulation, owner-bound human confirmation, immutable policy
history and fail-closed product-condition restrictions.

**Disabled by default.** Requires NATURAL_LANGUAGE_WALLETS_ENABLED=true.
The compiler accepts a closed English grammar. General-purpose language
understanding, production human authentication and live Shopify draft import
are not claimed. See release blockers below.

No financial transaction, production migration/deployment, secret inspection,
Shopify checkout, commit or push occurred. Pre-existing V11.4.9 uncommitted
changes were preserved.

## Architecture and AI compilation workflow

~~~mermaid
flowchart TD
 A[Authenticated instruction] --> B[Existing ownership gate and SQL quotas]
 B --> C[Closed grammar and explicit source provenance]
 C --> D[Missing values / contradictions / unsupported clauses]
 D --> E[Clarification and structured human review]
 E --> F[Strict DraftWalletPolicy schema]
 F --> G[Canonical JSON, SHA-256 and owned expiring draft]
 G --> H[Deterministic hypothetical simulation]
 G --> I[Explicit human confirmation of exact digest]
 I --> J[Atomic draft claim, wallet and ownership creation]
 J --> K[Immutable policy history]
 K --> L[Existing policy, risk, reservation and payment boundaries]
~~~

Implementation is separated into compiler.ts, routes.ts and repository.ts under
apps/worker/src/wallet-authority. The existing Worker dispatches these routes
through the default-deny financial access gate.

The existing AI parser was inspected. Its INR default, assumed quantity and
generated expiration belong to a different purchase-intent contract and would
invent wallet permissions. It is not reused. **No remote model runs in the wallet
compiler.** Every supported clause is deterministically recognized; unrecognized
text cannot be discarded because it might contain a restriction. There is no
model fallback that can broaden authority. Strict schemas reject malformed
model-shaped/client JSON and unknown authority keys.

DraftWalletPolicy explicitly requires currency, total budget, autonomous limit,
hard ceiling, categories, brand allow/block lists, required features, condition
exclusions and UTC expiration. Monetary validation includes precision, storage
bounds and auto <= hard ceiling <= total budget. New drafts reject three-decimal
authority unsupported by the existing NUMERIC(14,2) storage. Existing money
storage is unchanged.

Missing values require clarification. Contradictory currencies, limits, brands
and conditions are rejected. Dollar symbols, currency names, localized number
separators, slash dates, “tomorrow”, “next Friday”, unsupported compound clauses,
and trailing injected instructions are not silently interpreted. Repeated
conflicting values fail validation.

Name has a labelled display-only default; country defaults to ZZ, explicitly
labelled unknown rather than inventing a jurisdiction. No default budget,
threshold, hard ceiling, currency, duration or category is supplied.

Recognized example:

~~~text
Give my shopping agent 100 USD for one day.
Allow Sony and Bose electronics.
Auto limit 50 USD.
Hard ceiling 75 USD.
No blocked brands.
No required features.
New only.
Country US.
~~~

Other clauses include Budget, Total budget, Categories, Brands, Any brands,
Block brands, Require features, Any product condition, Must never buy refurbished
products, Name and exact UTC timestamps such as Expires 2027-01-01T00:00:00Z.
Durations accept digits and one through seven in words; durations beyond 365
days require clarification.

The mission example is incomplete: “must ask above 5000” defines an autonomous
approval threshold, not a hard transaction ceiling. The compiler requires a
separate ceiling and explicit unspecified restriction choices.

## Frontend experience

WalletAuthorityComposer is integrated into the existing Wallets page while
retaining the manual creator, wallet list, simulator and step-up controls.

Instructions produce clarification messages and editable structured rules.
EXPLICIT, HUMAN EDIT, DISPLAY_DEFAULT and UNKNOWN_COUNTRY distinguish provenance.
No inferred brand, category or condition becomes permission. Missing restriction
lists require explicit entry of “none” for an unrestricted choice.

The preview shows DRAFT / NOT AUTHORIZED, total budget, thresholds, categories,
brands, features, exclusions, expiration, canonical JSON and digest. Editing any
field or instructions clears the current challenge, simulation and consent.
Structured edits create a fresh preview. A dedicated checkbox and confirmation
action approve the exact previewed digest.

The component handles pending requests, API outages/rejections, malformed or
incomplete responses and field-level validation messages. Controls, wrapping
and grid layout support desktop/mobile. Screenshot review caught and corrected
textarea contrast. Active wallets display condition exclusions and explain
unverified-condition blocking.

## Human confirmation and security

| Route | Purpose |
| --- | --- |
| POST /api/wallet-authority/compile | Parse; persist only complete valid drafts |
| POST /api/wallet-authority/preview | Validate explicit structured edits; issue a fresh draft |
| POST /api/wallet-authority/simulate | Evaluate an owned, valid, unconsumed draft |
| POST /api/wallet-authority/confirm | Confirm exact owned draft ID and digest |
| GET /api/wallet-authority/history/:walletId | Read versions through wallet ownership/read permission |

Canonical draft JSON sorts keys and array sets. The server stores its SHA-256,
principal, challenge ID, provenance and expiry. The database independently
checks digest/content agreement. Review expires after at most ten minutes and
never outlives policy expiration.

Confirmation accepts only draftId, digest and humanConfirmed:true; replacement
policy fields are rejected. It rechecks ownership, expiry, digest, strict schema
and canonical integrity. A single SQL statement conditionally consumes the draft
and inserts the wallet and financial owner. The history trigger participates
in the same statement. Failure rolls everything back. Competing confirmations
create exactly one wallet. Changed digest, extra fields, stale/consumed draft,
cross-user access and replay fail closed.

Machine API and WhatsApp credentials cannot confirm through this route.
Existing authenticated sandbox browser capabilities and operators can confirm.
Sandbox USD 100, one-day expiry, creation/IP quotas and mutation nonce rules
remain enforced. This is explicit approval within the existing identity model;
it does not create a production account-login, MFA or proof-of-human system.

All draft POSTs require the existing wallet:create scope. Owner checks use
server-derived identity. Bodies remain bounded to 16 KiB and instructions to
4,000 characters. Shared SQL quotas allow six authority requests per
principal/minute and sixty globally/minute, plus existing IP/principal/mutation
limits. Invalid confirmations also consume conservative creation quotas.
Draft IDs and client ownership assertions cannot change the authenticated owner.

## Schema changes and policy versions

Migration apps/worker/db/v11_5_wallet_authority.sql follows the 18 baseline
migrations in release-order.json. It was applied only to disposable databases.

- Adds intent_wallets.excluded_conditions, with an empty historical default and
  enumerated NEW / USED / REFURBISHED values.
- Adds wallet_authority_drafts for owner-bound canonical confirmation challenges.
- Adds wallet_policy_versions, canonical snapshots, digests and history triggers.
- Adds an UPDATE/DELETE rejection trigger for version rows.
- Seeds additive baseline snapshots without changing prior transaction evidence.

History digests hash PostgreSQL JSONB text of the full policy and status.
This is a different canonical representation from human-review draft JSON.
Both exact canonical strings are retained and independently hash-verifiable.
The consumed draft retains its confirmed digest and created-wallet relationship.

Policy changes, including existing authorized step-up auto-limit changes, append
versions. Spend/reservation-only changes do not create spurious versions.
Wallet-row locking serializes policy updates. Prior decisions, quote hashes,
receipts and ledger evidence are not rewritten. Application UPDATE/DELETE
cannot overwrite history; privileged database administration/TRUNCATE is outside
this guarantee. No historical human actor attribution is invented.

No new route lets a model modify an existing wallet. Existing mutation paths
retain server-side authorization. This release edits drafts before creation and
records existing authorized changes; it does not provide a general in-place
wallet-policy editor.

## Product conditions and simulation

NEW ONLY excludes USED and REFURBISHED. “Never refurbished” excludes REFURBISHED.
Unknown condition fails closed for either rule.

The actual shared wallet engine returns BLOCK / PRODUCT_CONDITION_UNVERIFIED
whenever condition verification is required. Current adapters provide no
independently verified condition evidence. Descriptions, titles, model inference,
feature strings, browser assertions and “verified” labels cannot clear the rule.
The shared repository carries exclusions into commerce, authorization, step-up,
session orchestration and fresh payment evaluation. Integration tests prove
a strict-condition wallet creates no executable purchase or reservation.

Simulation calls the real evaluateWalletTransaction engine and displays its
ALLOW / STEP-UP / BLOCK reasons. It persists no decisions, risk observations,
grants, sessions, holds or payments, and disables executable authority.

Hypothetical facts are labelled hypothetical. Shopify mode accepts manually
supplied hypothetical transaction facts and discards unverified brand/category/
features. It does not fetch Shopify, attest availability, normalize live FX or
certify copied data as a quote. A direct draft-to-live-Shopify importer is not
implemented. Existing live discovery remains on the existing wallet-owned
commerce route, with checkout disabled.

Simulation is a base-policy test, not adaptive-risk clearance. Existing risk
still only tightens actual commerce/execution decisions.

## Financial separation

Compilation, preview and simulation cannot create a wallet, reserve funds,
issue STEP-UP authority or initiate payment. Confirmation creates only a wallet
and ownership/history records. No compiler route invokes a payment connector.

PayPal recipient binding, durable reservations, verified settlement, signed
receipts and refund controls remain unchanged. Shopify checkout remains blocked.
Condition exclusions can only tighten decisions. Historical receipt and quote
canonicalizers are unchanged.

## Model limitations and production release blockers

1. Keep the feature disabled until migration 19, prerequisites, consistent
   consumers, privileges, rollback and retention have been reviewed. No
   production migration or deployment occurred.
2. Integrate production human identity/MFA and approval provenance. Current
   activation supports existing sandbox capabilities/operators. Machine API
   credentials remain insufficient.
3. The closed English grammar intentionally requires clarification for
   unsupported language, localized notation and compound clauses. No general
   semantic or multilingual completeness is claimed. A future LLM must remain
   untrusted and cannot import the legacy parser's financial defaults.
4. Independent condition attestation is absent. Strict-condition wallets cannot
   purchase until verified evidence is implemented. Never loosen this guard by
   trusting merchant text.
5. Live Shopify draft import and risk-aware scenario forecasting are absent.
   Hypothetical simulation is not payment or checkout readiness.
6. Existing V11.4.8/V11.4.9 live-payment NO-GO gates remain: actual PayPal account,
   recipient approval, provider permissions, authentic live webhook evidence,
   dependency advisories, deployed infrastructure, recovery and retention.
   Isolated mocked payment tests are not live financial evidence.

The fresh browser bridge stopped cleanly through its test-only stop endpoint.
All disposable PostgreSQL test databases were dropped and the fresh server
was stopped successfully. The original task-owned Next development server
could not be terminated through Windows process tools in this sandbox.

Production build used an isolated .validation/next-build output directory to
avoid overwriting the running browser server output. The temporary Next config
and generated TypeScript config changes were restored after the successful
build. Build-only API URL was https://build-only.invalid; no deployment occurred.
